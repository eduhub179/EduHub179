# Замены уроков — реализация

> Статус: **реализовано** (встроено в архитектуру `lesson_instances`).
> Журнал решений от 2026-08-16 (Max + Alan); заменяет более ранний дизайн с отдельной таблицей.

## 1. Зачем это нужно

Учитель отсутствует или занят → другой учитель ведёт этот один урок. Слот (день/время)
остаётся; меняется только содержание (предмет, учитель, кабинет). Обмен предметами между
двумя слотами тоже возможен, но редок.

## 2. Модель

Три уровня, без изменений:

| Уровень | Что это | Как часто меняется |
|---|---|---|
| `lessons` | класс/группа + предмет + учителя (через `lesson_teachers`) | редко |
| `lesson_templates` | день + время + чётность, `is_active` | иногда (общешкольное изменение) |
| `lesson_instances` | конкретный урок на конкретную дату, `status` | каждый раз (по неделям) |

**Замена — это не отдельная таблица.** Это операция на уровне инстансов:

1. **Отменить** исходный инстанс: `status = 'cancelled'`.
2. **Создать** замещающий урок (тот же класс/группа, новый учитель/предмет если нужно).
3. **Создать** замещающий шаблон для этого урока (тот же слот день/время).
4. **Создать** замещающий инстанс на эту неделю, `status = 'scheduled'`.

Исходный инстанс остаётся в БД (история, аудит) и отображается в расписании серым
(`get_student_schedule_for_date` возвращает отменённые строки со статусом). Замещающий
инстанс отображается как обычный запланированный урок.

## 3. Почему не отдельная таблица

Более ранний дизайн предлагал таблицу `lesson_overrides`. Он был отклонён в пользу
уровня инстансов, потому что:

- **Проще.** Ни новой таблицы, ни нового репозитория, ни нового агрегата. Переиспользует
  существующую механику `lessons` + `lesson_templates` + `lesson_instances`.
- **Нет лишней схемы.** Колонка `is_override` на `lesson_templates` (наследие старого
  процесса замен) удалена — она всегда была `FALSE` и не несла смысла.
- **История сохранена.** Отменённый исходный инстанс — это журнал аудита.
  «Что было здесь до замены?» → смотрим на отменённый инстанс.
- **Проверка занятости уже поддерживает это.** `check_teacher_available` имеет параметр
  `p_exclude_instance_id` — он пропускает отменённый инстанс при проверке свободен ли
  замещающий учитель.

## 4. Процесс

**Замена учителя на один урок:**

1. Проверить, что замещающий учитель свободен:
   ```sql
   SELECT check_teacher_available(
       'substitute_teacher_id'::UUID,
       '2026-09-07'::DATE,  -- week_start_date
       'mon'::day_of_week,
       '10:50'::TIME,
       '11:35'::TIME,
       'original_instance_id'::UUID  -- исключаем заменяемый инстанс
   );
   ```
2. Отменить исходный инстанс:
   ```sql
   UPDATE lesson_instances SET status = 'cancelled' WHERE instance_id = 'original_instance_id';
   ```
3. Создать замещающий урок + учителей + шаблон + инстанс (если замещающий урок уже
   существует — переиспользовать его).

**Восстановление:** установить замещающему инстансу `cancelled`, а исходному — `scheduled`.

### Пример — разовый обмен предметами между двумя слотами

«На этой неделе: вместо литературы в понедельник — алгебра, вместо алгебры в четверг —
литература.»

- Отменить инстанс литературы в понедельник + инстанс алгебры в четверг.
- Создать замещающие инстансы, указывающие на существующие уроки алгебры и литературы
  (тот же класс, те же учителя — переиспользуем строки уроков).
- Оба слота остаются на месте; меняется только содержание.

Для **постоянной** договорённости — правим шаблоны (шаблон понедельника указывает на
алгебру, четверга — на литературу). Это уровень «шаблоны меняются иногда», а не замена.

## 5. Проверка занятости учителя

```sql
check_teacher_available(
    p_teacher_id UUID,
    p_week_start_date DATE,
    p_day day_of_week,
    p_start_time TIME,
    p_end_time TIME,
    p_exclude_instance_id UUID DEFAULT NULL
)
```

Два уровня:

- **У недели есть инстансы** (сгенерированы): сканирует `lesson_instances` этой недели
  со `status = 'scheduled'`. Отменённые инстансы (исходный, который заменяется) не блокируют.
  `p_exclude_instance_id` также пропускает заменяемый инстанс (двойная безопасность).
- **У недели ещё нет инстансов** (ленивая генерация): откат на активные шаблоны.
  Чисто, потому что замены никогда не трогают шаблоны.

## 6. Взаимодействие с ДЗ

ДЗ привязано к `lesson_instances`.

- **Тот же предмет** (замена учителя): ДЗ остаётся на исходном инстансе; замещающий
  учитель работает с ним как обычно.
- **Предмет изменился:** ДЗ переезжает на следующий запланированный инстанс исходного
  урока. Если этого инстанса ещё нет (ленивая генерация) — создаём по требованию.

## 7. Отображение — ничего не скрывается автоматически

Каждое занятие, в котором участвует ученик, показывается; пересечения помечаются;
решает ученик.

- Отменённые уроки появляются в `get_student_schedule_for_date` со
  `status = 'cancelled'` — клиент рендерит их серым.
- Замещающие инстансы появляются как обычные запланированные уроки.
- События, в которых ученик участвует, появляются отдельными строками. Разметка
  пересечений — на стороне клиента.
- Урок, заменённый обязательным событием, отменяется через статус инстанса —
  отображается «отменён» + событие. Скрытие не нужно.

Учителя — другое дело: пересечения **предотвращаются** проверкой занятости, а не
показываются как выбор. Известный пробел: организаторы событий ещё не покрыты
`check_teacher_available` — будущая функция UI, без влияния на схему.

## 8. Что было удалено

- Колонка `lesson_templates.is_override` — удалена из миграции 0003. Она всегда была
  `FALSE` и не несла смысла с подходом на уровне инстансов.
- Предложенная таблица `lesson_overrides` — никогда не создавалась, не нужна.

## 9. Замена учителя и заметка из админ-панели (`lesson_substitutions`, 2026-10-23)

Процесс из раздела 4 не работает для самого частого случая — **тот же предмет, другой
учитель**: замещающий урок нельзя создать, потому что `lessons` уникален по
`(class_id, subject_id)` / `(group_id, subject_id)`, а `lesson_templates` — по
`(lesson_id, day, start_time, end_time, parity)`. Кроме того, заметке для учеников
(«в актовом зале») негде храниться.

Поэтому админ-панель (`PATCH /api/admin/lessons/{instance_id}`) делает так:

- **Отмена** и **смена кабинета** — как раньше, на самом инстансе (`status`, `cabinet_id`).
- **Замещающий учитель** и **заметка** — строка в `lesson_substitutions`
  (миграция 0012, одна строка на инстанс, удаляется вместе с ним). Пустая замена
  (без учителя и без заметки) удаляется.
- Расписание (`ScheduleService`) показывает в `teachers` замещающего учителя, обычных —
  в `usual_teachers`, заметку — в `note`; урок попадает и в расписание замещающего учителя.
- ДЗ остаётся на том же инстансе. `copy_week` замены не копирует.

Процесс из раздела 4 остаётся для **смены предмета** (обмен предметами между слотами).
Известный пробел: `check_teacher_available` пока не учитывает `lesson_substitutions`,
и админка не проверяет, свободен ли замещающий учитель.

## 10. Редактор расписания в админ-панели (`TimetableService`, 2026-10-23)

Вкладка «Расписание» меняет **постоянное** расписание, вкладка «Замены и отмены» —
отдельные уроки. Код: `application/src/use_cases/admin/timetable_service.rs`,
маршруты `presentation/src/routes/timetable.rs`.

- **Курсы** (`lessons`) и их учителя: `POST /api/admin/courses`,
  `PUT /api/admin/courses/{id}/teachers`. Учитель курса меняется для всех недель, в том
  числе прошедших; смена на один день — это замена (раздел 9).
- **Слоты** (`lesson_templates`): `POST /api/admin/slots`, `PUT|DELETE /api/admin/slots/{id}`.
  История не переписывается: изменённый слот становится новым шаблоном, старый
  деактивируется (`is_active = FALSE`). Уже созданные недели меняются только при
  `apply_from` — с этой даты уроки переводятся на новый шаблон. Урок с ДЗ никогда не
  меняет предмет (остаётся как был, счётчик `kept`); удалённый слот с ДЗ становится
  `cancelled`, без ДЗ — удаляется.
- **Разовый урок**: `POST /api/admin/lessons` — урок на одну дату. Создаётся
  **неактивный** шаблон, поэтому `generate_from_templates` и `copy_week` его не
  переносят в другие недели. Если в этом слоте уже есть отменённый урок, он
  восстанавливается, а не дублируется.
- **Перенос урока**: `POST /api/admin/lessons/{id}/move` — исходный урок становится
  `cancelled`, в новом месте добавляется разовый урок, ДЗ переезжает вместе с ним
  (это процесс раздела 4, только автоматически).
- `copy_week` теперь пропускает уроки неактивных шаблонов (разовые и убранные из
  расписания).
- Разовые и перенесённые уроки помечаются `lesson_instances.is_extra = TRUE`
  (миграция 0013; урок, вернувшийся в свой постоянный слот, — снова `FALSE`).
  API расписания отдаёт `is_extra`; сайт подсвечивает такие уроки и уроки с заменой
  учителя (`usual_teachers`) бледно-синим с подписью «новый урок» / «замена».

Известные пробелы: нет проверки, что класс, учитель или кабинет свободны в это время
(пересечение проверяется только внутри одного курса); чётность недели при генерации
пока не учитывается (как и раньше в `generate_from_templates`); групповой курс
виден в расписании класса, только если в группе есть ученики этого класса.
