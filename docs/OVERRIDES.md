> Статус: **дизайн, не реализовано.** Журнал решений от 2026-08-16 (Max + Alan).

> и §5.6/§6.1 (затенение событий → заменено отображением пересечений, см. §7).

## 1. Зачем это нужно

У старого процесса замен (новый урок + новый шаблон с `is_override = TRUE` + перенаправление
экземпляра) было три структурных проблемы:

1. **Проверка занятости не знает о неделях.** `check_teacher_available(teacher, day, start, end, exclude_template_id)`
   сканирует *все активные шаблоны* и не имеет параметра даты/недели. Шаблон замены на одну
   неделю блокировал замещающего учителя на это время **каждую** неделю, пока его не
   заархивировали вручную.
2. **Нет связи «замена → оригинал».** Ничто структурно не говорит «этот урок заменил тот».
   «Заменён на» невозможно было показать; архивирование было ручным ритуалом.
3. **Громоздкий ритуал.** Обмен на одну неделю требовал клонирования урока (дедуп-индекс
   `(lesson_id, day, start_time, end_time, parity)` блокирует второй шаблон для того же урока
   в том же слоте), создания шаблона и перенаправления экземпляра.

## 2. Модель

Три уровня остаются без изменений:

| Уровень | Изменения | Пример |
|---|---|---|
| `lessons` | крайне редко | класс/группа + предмет + учителя (через `lesson_teachers`) |
| `lesson_templates` | иногда (общешкольное изменение расписания) | день + время, `is_active` |
| `lesson_instances` | каждый раз | конкретный урок на конкретную дату, `status` |

**Замена — это боковой канал, прикреплённый к одному экземпляру:** «это занятие проходит
с другим содержанием». Она меняет *что преподаётся и кем*, но никогда *когда/где*:

- Слот (день/время) всегда берётся из цепочки экземпляр → шаблон. Замена не может
  переместить урок. Переносы — это работа расписания (правка шаблона для постоянного
  изменения, генерация экземпляра для разового).
- Основной реальный сценарий: в класс приходит другой учитель, потому что основной
  отсутствует или занят. Смена предмета возможна, но редка.

## 3. Новая таблица

```sql
CREATE TABLE lesson_overrides
(
    override_id UUID PRIMARY KEY     DEFAULT gen_random_uuid(),
    instance_id UUID        NOT NULL REFERENCES lesson_instances (instance_id) ON DELETE CASCADE,
    lesson_id   UUID        NOT NULL REFERENCES lessons (lesson_id) ON DELETE RESTRICT, -- replacement lesson
    comment     TEXT NULL,          -- "Ivanov is sick, Petrov covers"
    created_by  UUID        NOT NULL REFERENCES users (user_id),
    revoked_at  TIMESTAMPTZ NULL,   -- NULL = active
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- One ACTIVE override per instance; unlimited revoked history
CREATE UNIQUE INDEX idx_lesson_overrides_one_active
    ON lesson_overrides (instance_id)
    WHERE revoked_at IS NULL;
```

Ключевые свойства:

- **Замена — это настоящая строка `lessons`.** Учителя живут только в `lesson_teachers`
  (связь многие-ко-многим, не привязана к неделе), поэтому смена учителя требует нового
  урока: тот же класс/группа, предмет может измениться или остаться, новый(е) учитель(я).
  Переиспользуется вся существующая механика — ни новой M2M-таблицы, ни дублирующей
  валидации.
- **Один урок может стоять за многими заменами.** «Петров ведёт ВСЕ понедельники Иванова
  на этой неделе» = 1 строка урока + N строк замен (по одной на экземпляр).
- **Посещаемость всегда вычисляется из ИСХОДНОЙ цепочки** (экземпляр → шаблон → класс/группа
  исходного урока). Замена добавляет только предмет + учителей. Правило уровня приложения:
  заменяющий урок должен быть на тот же класс/группу. Это исключает ловушку несовпадения
  классов.
- **Нет жёсткого удаления.** Восстановление = установить `revoked_at`. История служит
  и справочником для администратора («когда Петров в прошлый раз замещал Иванова»),
  и журналом аудита.
- **На замене нет полей день/время.** Идентичность слота — это дело экземпляра.
- События **не** часть этой таблицы, и уникальный индекс их не учитывает — событие
  перекрывает занятие точечно для ученика (`event_attendees`), поэтому событие и замена
  могут легально сосуществовать (участники видят событие, все остальные — заменённый урок).

## 4. Процесс

**Замена урока:**
1. Проверка занятости (с учётом недели, см. §5).
2. Создать заменяющий урок, если его ещё нет (тот же класс/группа; предмет и учителя — по
   необходимости).
3. `INSERT INTO lesson_overrides (instance_id, lesson_id, comment, created_by)`.

**Восстановление:** `UPDATE lesson_overrides SET revoked_at = now() WHERE override_id = ...`.

Никакой хирургии с шаблонами, никакого перенаправления экземпляров, никакого обхода
дедуп-индекса.

### Пример — разовый обмен предметами между двумя слотами

«На этой неделе: вместо литературы в понедельник — алгебра, вместо алгебры в четверг —
литература». Оба слота остаются на своих местах; меняется только содержание:

- **Разово (одна неделя):** две замены — экземпляр понедельника → урок алгебры, экземпляр
  четверга → урок литературы. Если обмениваемые уроки принадлежат одному классу и учителя
  совпадают, существующие строки уроков переиспользуются напрямую — новые уроки не нужны.
- **Постоянная договорённость:** правим шаблоны (шаблон понедельника указывает на алгебру,
  четверга — на литературу). Это уровень «шаблоны меняются иногда», а не замена.

Оба случая остаются внутри модели — никакой механики переноса слотов.

## 5. Проверка занятости

```sql
check_teacher_available(
    p_teacher_id UUID,
    p_week_start_date DATE,
    p_day day_of_week,
    p_start_time TIME,
    p_end_time TIME,
    p_exclude_instance_id UUID DEFAULT NULL
)
```

Два уровня:

- **У недели есть экземпляры** (сгенерированы): сканируем `lesson_instances` этой недели
  с `status = 'scheduled'`; фактический урок = `COALESCE(активная замена.lesson_id,
  template.lesson_id)`; учителя через `lesson_teachers`. Пересечение по (день, время).
- **У недели ещё нет экземпляров** (ленивая генерация): откат на **активные шаблоны**.
  Этот откат снова чист *потому, что* замены никогда не трогают шаблоны — старый баг
  «слепоты к неделям» был вызван тем, что шаблоны замен засоряли пространство шаблонов.

Следствие ленивой генерации: замена может указывать только на уже существующий экземпляр
(недели генерируются по одной).

## 6. Домашние задания

ДЗ привязано к `lesson_instances`. Правило при замене:

- **Тот же предмет** (обычный случай — замена учителя): ДЗ остаётся на экземпляре;
  замещающий учитель работает с ним как обычно.
- **Предмет изменился:** ДЗ переезжает на **следующий запланированный экземпляр исходного
  урока** (исходный предмет + учитель). При ленивой генерации целевого экземпляра может ещё
  не быть — создаём его по требованию (это и есть реальный будущий урок).

Отложенные крайние случаи: «сирота» в конце учебного периода (следующего вхождения нет),
откат перенесённого ДЗ при отзыве замены.

## 7. Отображение (для ученика) — ничего не скрывается автоматически

**Каждое занятие, в котором участвует ученик, показывается; пересечения помечаются;
решает ученик.** Это относится и к урокам, и к событиям, и к кружкам — участие всегда
выбор ученика, поэтому система показывает конфликт, а не прячет одну из сторон
(решение 2026-08-16):

- Содержимое строки урока: активная замена > оригинал (замена меняет то, что преподаётся).
- Строка события: показывается, если ученик — участник и событие пересекается со слотом урока.
- Обе строки появляются с маркером конфликта, когда пересекаются.
- Урок, заменённый обязательным событием, **отменяется через статус экземпляра**
  (`status = 'cancelled'`) — в представлении «отменён» + событие. Скрытие не нужно.

Следствия для `get_student_schedule_for_date`: убрать исключение событий через `NOT EXISTS` —
уроки и события участника возвращаются отдельными строками; разметка пересечений — на
стороне клиента.

**Учителя — другое дело: предотвращать, а не показывать.** Учитель не может разорваться
между двумя кабинетами, поэтому пересечения предотвращаются проверкой занятости, а не
показываются как выбор. Известный пробел, который закроем позже: организаторы событий
сегодня НЕ покрыты `check_teacher_available`. Предупреждения о пересечениях для учителей —
функция UI на потом — без влияния на схему.

## 8. Изменения схемы (будущая миграция, ещё не написана)

- НОВАЯ `lesson_overrides` (+ частичный уникальный индекс, FK) — §3.
- `lesson_instances` + `cabinet_id UUID NULL` — кабинеты переезжают на экземпляры
  (еженедельная ротация кабинетов без правки шаблонов; честные запросы «свободный кабинет»).
  В шаблоне `cabinet_id` пока остаётся; убирать ли его — отложенная оптимизация памяти
  (архивам информация о кабинете не нужна).
- `lesson_templates`: убрать `is_override` (шаблонов-замен больше нет).
- `check_teacher_available`: новая сигнатура с учётом недели (§5).

## 9. Отложено / помечено на потом

- **Колонка кабинета в шаблонах**: оставить обе, решить позже.
- **Таблица событий**: оставить. Она обслуживает разовые активности (лекции, олимпиады,
  экскурсии): абсолютные временные метки, список участников, затенение. Регулярные
  внеучебные активности (волейбол, доп. информатика) — это НЕ события: это шаблоны +
  `student_groups` + `subjects`, с `week_parity` для кружков через неделю.
  Дедуп-индекс уже учитывает чётность, поэтому шаблоны-близнецы (нечёт/чёт) сосуществуют.
- **Генерация расписания** (копирование предыдущей недели → следующей, затем применение
  замен): отдельное обсуждение, здесь не проектируется.
- **Разрешение пересечений кружок/урок** (реальные случаи, Max 2026-08-16): кружок ученика
  может пересекаться с обычным уроком (или другим кружком), события — с уроками. Единое
  правило (см. §7): показывать все строки + маркер конфликта, решает ученик — ничего не
  скрывается автоматически. Отменённые уроки: решено 2026-08-16 — показывать серым
  (решение об отображении, не о схеме). Предупреждения о пересечениях для учителей +
  проверка организаторов событий: позже.
- **Эксклюзивный индекс двойного бронирования кабинета** (одна комната, одно время — уроки,
  кружки и события вместе): стоит построить в итоге; отложено вместе с решением по кабинетам.
