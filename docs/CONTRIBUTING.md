# 📜 Стандарт документирования кода (SQL & Rust)

**Цель:** Сделать код самодокументируемым. Любой разработчик должен понять назначение сущности, ее ограничения и причины архитектурных решений, не покидая файл.
**Главное правило:** Комментарии объясняют **«почему»** и **«какие гарантии дает»**, а не дублируют название переменной. Комментарии должны быть **короткими**.

---

## 🗄️ Часть 1. Стандарт для SQL (Миграции)

### 1. Шапка файла (Обязательно)
Каждый файл миграции должен начинаться с этого блока.
```sql
-- ============================================================================
-- ФАЙЛ: 000X_<имя_сущности>.sql
-- НАЗНАЧЕНИЕ: Кратко (1 предложение), что создает файл.
-- ЗАВИСИМОСТИ: [000Y_файл.sql] или "Нет".
-- МАСТЕР-ДОКУМЕНТ: Раздел X.Y
-- ============================================================================
```

### 2. Таблицы и поля
*   Группируйте логически связанные поля.
*   Пишите комментарий **над** полем или группой полей.
*   Если имя поля не дает полной информации (формат, ограничения, единицы измерения), это **обязательно** указывается в комментарии.

```sql
CREATE TABLE homework_files
(
    file_id      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    homework_id  UUID NOT NULL REFERENCES homeworks(homework_id) ON DELETE CASCADE,
    
    -- Ссылка на объект в S3. 
    -- ВАЖНО: На уровне приложения гарантируется, что это только .pdf или .jpg.
    s3_url       VARCHAR(500) NOT NULL,
    
    -- Размер файла в байтах. Нужен для квот и быстрой проверки целостности при скачивании.
    size_bytes   BIGINT NOT NULL CHECK (size_bytes > 0),
    
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### 3. Индексы (Обязательное обоснование)
Каждый индекс должен иметь комментарий, отвечающий на два вопроса: **какой запрос ускоряет** и **почему выбран такой тип** (особенно для частичных индексов).

```sql
-- ИНДЕКС: idx_homework_files_homework
-- Цель: Ускоряет выборку всех файлов конкретного ДЗ при рендеринге страницы.
-- Тип: Обычный B-дерево, так как запросы идут по точному совпадению homework_id.
CREATE INDEX idx_homework_files_homework ON homework_files (homework_id);

-- ИНДЕКС: idx_users_active_students
-- Цель: Ускоряет поиск учеников для выставления оценок.
-- Тип: Частичный (WHERE is_active = TRUE). Уменьшает размер индекса и ускоряет поиск, 
--      так как неактивные пользователи в этом сценарии не нужны.
CREATE INDEX idx_users_active_students ON users (last_name, first_name) 
WHERE role = 'student' AND is_active = TRUE;
```

### 4. Функции и Триггеры
Краткое описание назначения, входных данных и fail-safe гарантий.

```sql
-- ФУНКЦИЯ: check_teacher_available
-- Назначение: Проверка пересечения расписания учителя.
-- Fail-safe: Игнорирует архивные шаблоны (is_active = FALSE), предотвращая ложные конфликты.
-- Возвращает: TRUE, если учитель свободен в указанный интервал.
```

## 🦀 Часть 2. Стандарт для Rust

Учитывая ваше предпочтение к инкапсуляции, отсутствию паник (fail-safe) и заботе о производительности, стандарт для Rust строится вокруг этих принципов.

### 1. Шапка модуля/файла (Обязательно)
```rust
//! Модуль отвечает за управление расписанием уроков.
//! 
//! Зависимости: `crate::users`, `crate::database`
//! Гарантии: Все публичные методы возвращают `Result` или `Option`, паники недопустимы.
```

### 2. Структуры (Structs) и Инкапсуляция
Используйте `///` для документации публичных структур. Описывайте инварианты (что гарантирует эта структура). Поля с неочевидным назначением комментируются через `//`.

```rust
/// Шаблон урока в расписании.
/// 
/// Инвариант: `end_time` всегда строго больше `start_time`. 
/// Гарантируется на уровне валидации перед сохранением в БД.
pub struct LessonTemplate {
    pub id: Uuid,
    pub lesson_id: Uuid,
    
    /// Периодичность: каждую неделю, только четные или только нечетные.
    pub parity: WeekParity,
    
    is_active: bool,
}
```

### 3. Функции и Методы
Публичные функции документируются через `///`. Обязательно указывайте, как функция ведет себя при некорректных данных (fail-safe).

```rust
impl LessonTemplate {
    /// Проверяет, доступен ли учитель в заданное время.
    /// 
    /// # Fail-safe поведение
    /// Возвращает `Ok(true)`, если учитель свободен. 
    /// Возвращает `Ok(false)` при любом пересечении.
    /// Возвращает `Err`, только при сбое соединения с БД (не паникует).
    pub async fn is_teacher_available(
        &self,
        db: &DatabasePool,
        teacher_id: Uuid,
    ) -> Result<bool, DbError> {
        // ...
    }
}
```

### 4. Сложная логика и оптимизации (Inline comments)
Если используется низкоуровневая оптимизация, персистентная структура данных или неочевидный алгоритм, добавьте короткий комментарий `//`, объясняющий **почему** это сделано именно так.

```rust
pub fn calculate_schedule_matrix(&self, students: &[Student]) -> Matrix {
    // Используем плоский массив и AVX-инструкции вместо вложенных циклов,
    // так как профиль показал, что это дает 3-кратный прирост производительности 
    // при количестве учеников > 500.
    let mut matrix = Matrix::with_capacity(students.len());
    // ...
}
```

## ✅ Чек-лист для Code Review (Проверка перед мержем)

Применяйте этот чек-лист к себе и команде при ревью кода:

- [ ] **SQL/Rust:** В начале файла есть шапка с назначением и зависимостями?
- [ ] **SQL:** У всех неочевидных полей (форматы, единицы измерения, специфические ограничения) есть короткий комментарий *над* ними?
- [ ] **SQL:** У *каждого* индекса есть комментарий, объясняющий, какой запрос он ускоряет и почему выбран его тип?
- [ ] **Rust:** У публичных структур и методов есть `///` документация?
- [ ] **Rust:** Описано ли fail-safe поведение функций (что возвращается при ошибке, отсутствие паники)?
- [ ] **Общее:** Комментарии короткие, по делу и объясняют «почему», а не дублируют имя переменной?
