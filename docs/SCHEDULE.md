# Построение расписания (недели) — дизайн

> Статус: **реализовано частично.** Журнал решений от 2026-08-16 (Max + Alan).
> Миграция 0006 (`feat/schedule-layer`) уже сделала: `schedule_weeks`, FK экземпляр → неделя,
> гейт опубликованных недель и неделе-зависимую проверку занятости.
> Ещё не реализовано: сетка (шаблон недели, §4), операции сборки (§6) и правило правки
> опубликованной недели (§7). Копирование предыдущей недели — отдельная отложенная тема.

## 1. Мотивация

Экземпляры генерируются **лениво, неделя за неделей** — расписание нестабильно, пока не
закончится первый учебный период. **Неделя — единица построения расписания**: администратор
«собирает неделю», а (когда появится копирование) «копирует прошлую неделю в эту», затем
публикует. Неделе нужно существовать как первоклассной сущности, чтобы у процесса, правил
целостности и правил видимости был дом.

## 2. Мысленная модель

Строки = недели, колонки = шаблоны, ячейки = **lesson_instances**. Это только мысленная
модель:

- **Строки реальны**: одна строка `schedule_weeks` на неделю (`week_start_date` = понедельник).
- **Колонки НЕ хранятся** — шаблон «участвует в неделе», имея экземпляр для этой недели.
  Ячейки сетки — это и есть экземпляры (`instance = (template_id, week_start_date)`).
- Неделя «знает» свои шаблоны/экземпляры через FK, а не через хранимые списки:
  `SELECT ... FROM lesson_instances WHERE week_start_date = $1`.

## 3. Таблица

```sql
CREATE TABLE schedule_weeks
(
    week_start_date DATE PRIMARY KEY,

    -- Lifecycle: admin builds a week as draft, publishes when final
    status          VARCHAR(20) NOT NULL DEFAULT 'draft'
        CHECK (status IN ('draft', 'published')),

    -- Provenance: which week this one was copied from (NULL = generated from templates / manual)
    copied_from     DATE NULL REFERENCES schedule_weeks (week_start_date),

    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

- `lesson_instances.week_start_date` получает FK → `schedule_weeks.week_start_date`.
  Процесс администратора: **создать неделю → наполнить её экземплярами**. Больше никаких
  экземпляров, плавающих в неделях, которых не существует.
- Чисто аддитивно — сам `lesson_instances` остаётся ровно таким же. Домашние задания/файлы
  продолжают указывать на экземпляры как на стабильную единственную точку (вместо
  составного `(week, template)`).

## 4. Сетка (шаблон недели) — скелет слотов

`UNIQUE(template_id, week_start_date)` ограничивает экземпляры на (шаблон, неделя), но сами
шаблоны ничем не ограничены — ничто не мешает N шаблонам одного класса в один день/время
(дедуп-индекс построен на урок, а не на класс). Сетка закрывает эту дыру структурно.

Набор слотов — фиксированный общешкольный факт (одни и те же звонки каждый день): **enum**,
а не таблица — схема на каждое развёртывание; школа с другим расписанием звонков правит
значения в своей миграции.

```sql
CREATE TYPE lesson_slot AS ENUM
    ('lesson_1', 'lesson_2', 'lesson_3', 'lesson_4', 'lesson_5', 'lesson_6', 'lesson_7');

ALTER TABLE lesson_templates ADD COLUMN slot lesson_slot NULL;
```

- `slot` **необязателен для любого шаблона**. Назначенный слот помечает шаблон как часть
  официального расписания; время слота — константа в коде (`LessonSlot::bell_times()` в
  Rust) — единый источник правды: приложение автозаполняет и проверяет по нему
  `(start_time, end_time)` шаблона, так что администраторы не могут разойтись с расписанием
  звонков.
- **Флаг `is_regular` не нужен.** Настоящий инвариант един и прост: триггер-ограничение
  `chk_no_class_double_booking` блокирует любые два АКТИВНЫХ шаблона, нацеленных на один
  класс, с пересечением в `(day, start_time, end_time)` (с учётом чётности) — со слотом или
  без. Общеклассная активность в 15:30 работает, потому что ничего не пересекает; два
  урока одного класса в одно время невозможны.
- **Шаблоны групповых уроков (кружков) не блокируются никогда** — пересечения с сеткой и
  между собой легальны («решает ученик», OVERRIDES §7).
- Блокировка на уровне шаблонов: разовые подмены слота (урок заменён событием) идут через
  `status = 'cancelled'` у экземпляра, замены и сами события (OVERRIDES §7), а не через
  второй пересекающийся шаблон.
- Следствие: шаблоны со слотом ограничивают экземпляры на (класс, неделя) числом слотов,
  а бесслотовые классные шаблоны и так не могут пересекаться — обычное расписание не может
  «взорваться».

**Решение (2026-08-17): шаблоны остаются ОДНОЙ таблицей.** Признак класс/группа уже живёт
на `lessons` (class XOR group), и шаблоны наследуют его через FK. Разделение таблиц
потребовало бы XOR-колонок на `lesson_instances` и продублировало бы механику проверки
занятости/расписания без выгоды. Если когда-нибудь понадобится разделение на уровне типов —
оно живёт в домене (две сущности над одной таблицей), а не в схеме.

`week_parity` остаётся замороженной; здесь ничто не мешает шаблонам-близнецам (нечёт/чёт) —
дедуп-индекс их уже поддерживает.

## 5. Правила видимости

- **Ученики видят экземпляры только в ОПУБЛИКОВАННЫХ неделях.** Черновики доступны
  только администраторам.
- **Проверка занятости видит ВСЕ экземпляры, включая черновики** — сборка расписания
  должна предотвращать конфликты до того, как неделя выйдет в свет.
- Обратное заполнение миграцией: каждая неделя, у которой уже есть экземпляры, получает
  `status = 'published'`, чтобы после включения ограничения ничего не исчезло (сделано в 0006).

## 6. Сборка недели — операции

Обе операции создают неделю со статусом `draft`; затем администратор правит (замены,
отмены, кабинеты) и публикует.

### 6.1 Генерация из шаблонов

Для каждого активного шаблона создать экземпляр для целевой недели
(`lesson_date = week_start_date + day`); день/время берутся из шаблона (для классных
шаблонов они равны времени звонка слота, §4). Базовый сценарий для начала года /
нестабильного периода.

### 6.2 Копирование недели

`copy_week(source, target)` — процесс стабильного периода:

- Строка целевой недели создаётся как `draft`, если её нет; **ошибка, если у целевой недели
  уже есть экземпляры** (копирование только в пустые недели, без случайных слияний).
- Источник: по умолчанию предыдущая неделя, можно выбрать любую.
- Для каждого экземпляра источника → новый экземпляр: тот же `template_id`,
  `week_start_date = target`, `lesson_date = source + 7 days`, `status = 'scheduled'`
  (свежий — отмены привязаны к неделе и НЕ переносятся), `cabinet_id` копируется как
  отправная точка (администратор правит; защита — проверка свободного кабинета —
  автоматической валидации пока нет, см. OVERRIDES.md §9).
- **Замены НЕ копируются** — даже многонедельная замена («Иванов выбыл на 3 недели»)
  пересоздаётся каждую неделю, потому что замещающий учитель может меняться от недели
  к неделе (решение 2026-08-16).
- Безопасно по построению: ячейки соотносятся 1:1 на (template, week), поэтому
  `UNIQUE(template_id, week_start_date)` защищает от дублей; занятость ограничена неделей,
  значит, межнедельных конфликтов нет.
- `copied_from` фиксирует происхождение. Всё в одной транзакции.

## 7. Открыто / отложено

- **Правка опубликованной недели — РЕШЕНО (2026-08-16, гибрид):** возврат в черновик
  разрешён только для недель, которые ещё не начались (все уроки в будущем); как только
  неделя началась — только правка вживую: изменения применяются сразу, без скрытия.
  Чисто правило уровня приложения; колонки `status` уже достаточно.
- **Группировка по учебным периодам / годам**: позже.
- **Роль `template.cabinet_id` сужается до затравки недели 1** (дальше всё из копирования
  и правок) — связано с отложенным решением по колонке кабинета.
- **Изменения запросов — СДЕЛАНО в 0006**: `get_student_schedule_for_date` получает JOIN
  к `schedule_weeks` + фильтр `status = 'published'` и возвращает экземпляры, включая
  отменённые — серые строки решаются на стороне клиента (см. OVERRIDES.md §9).
- **Чётность, если когда-нибудь разморозят**: `generate_from_templates` и проверка
  занятости должны будут учитывать `week_parity` (нечётные/чётные недели). Дедуп-индекс уже
  поддерживает шаблоны-близнецы (нечёт/чёт). Сегодня фичи нет — колонка заморожена.
